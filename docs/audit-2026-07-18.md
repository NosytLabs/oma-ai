### Top 10 Issues (ordered by risk)

1. **SSRF TOCTOU in `/fetch` route** (`server/src/routes/fetch.ts`, `server/src/lib/url-safety.ts:109`) — DNS validation races actual fetch; attacker can rebind to internal IPs
2. **Gonka broker URL fix claimed but NOT landed** (`server/src/inference/provider-health.ts:396`) — prior audit `b63813a` was a false positive
3. **Hot wallet private key in Node process memory** (`server/src/x402/facilitator.ts:573`) — `FACILITATOR_PRIVATE_KEY` signs on-chain directly
4. **x402 facilitator DoS via Redis dependency** — `consumeNonce()` fails closed; no in-memory nonce fallback
5. **Withdrawal TOCTOU race** (`server/src/routes/withdraw.ts:179, 213`) — limit check outside transaction
6. **SIWE nonce not rotated on failed verification** (`server/src/auth/siwe.ts:129-141`) — unlimited replay attempts in 10min window
7. **CSRF token endpoint accepts GET** (`server/src/routes/auth.ts:517`) — sets cookie via GET (CSRF vector)
8. **`/v1/models` has no response cache** — 200+ model pricing lookups per request on hot path
9. **`/v1/credits/balance` hits DB on every chat request** — frontend polls every ~30s
10. **`UnifiedDepositInterface.tsx` (656L) and `DashboardGrid.tsx` (585L)** — over-large components with mixed concerns

### What's Strong

- Excellent centralized utilities (`lib/utils.tsx` used in 40+ components; `lib/validation.ts` used in 20+ routes)
- Strong Zod + Drizzle type discipline at the boundary
- Production-grade streaming token tracking (`stream-tracker.ts` with 250ms batching)
- Transactional withdrawals with `SELECT FOR UPDATE` on balance row
- Per-provider circuit breaker with async mutex
- Request deduplication via `Idempotency-Key` header
- Comprehensive `server/src/config.ts` Zod schema with production guards (fail-fast on insecure defaults)
- SIWE domain binding + JWT key rotation (`JWT_SECRET_PREVIOUS`)
- Strong a11y foundation: skip link, focus-visible, sr-only, aria-live, dynamic imports, ErrorBoundaries

### 1.2 Architecture Pattern

**Monorepo with pnpm workspaces** (no Turborepo/Nx). Two sibling apps:
- `app/` — Next.js frontend (port 3000)
- `server/` — Hono API (port 3001)

Backend uses **layered hexagonal-lite architecture**:
```
HTTP layer (routes/)  ──►  Middleware (auth, rate-limit, security, audit)  ──►  Services / Domain (inference/, credits/, x402/)  ──►  Persistence (db/)
```

Frontend uses **Next.js App Router with co-located routes**:
```
app/src/app/
├── (routes)              # Pages
│   ├── page.tsx          # Root layout
│   ├── _components/      # Shared
│   └── {feature}/
│       ├── page.tsx
│       ├── _components/  # Feature-local
│       └── _hooks/       # Feature-local
├── api/                  # Next.js API routes (proxy to server)
└── .well-known/          # Standards-compliant metadata
```

### 1.4 Coding Conventions

**Strengths (consistent across codebase):**
- Strict TypeScript everywhere
- Zod schemas at all boundaries (route inputs, env vars, config)
- Barrel files (`index.ts`) for shared modules
- Centralized utilities (`lib/utils.tsx` for formatting, `lib/validation.ts` for error shapes)
- Error code enums + structured `errorResponse` wrapper
- Pino structured logging with redacted fields
- Co-located tests (`__tests__/` next to source)
- Drizzle schema-first migrations in `db/migrations/`
- Per-page `_components/` and `_hooks/` to scope imports

**Inconsistencies:**
- DB columns are `snake_case` (Drizzle convention), TS uses `camelCase` — documented but slightly leaky at boundaries
- `truncateAddress` (verb) co-exists with `formatAddress` (noun) — see Phase 3 §2.1
- `boolean` prefixes mixed: `is_*`, `has_*`, `can_*`, `should_*` — no enforced convention
- Some pages mix `camelCase.tsx` filename with `kebab-case` (`quick-stats-card.tsx`) — minor
- Magic numbers scattered (timeouts, body limits, retry counts) — see Phase 3 §7

### 1.5 Component Hierarchy
