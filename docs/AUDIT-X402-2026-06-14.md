# x402 Payment Protocol — Security & Correctness Audit

**Date:** 2026-06-14
**Auditor:** opencode (M3) under ponytail mode
**Scope:** `server/src/x402/`, `server/src/inference/surplus.ts:282-364` (TRACKED ISSUE), `server/src/routes/x402.ts` (none — does not exist; x402 routes live in `facilitator.ts` and `crosschain.ts`)
**Commit:** HEAD (working tree; no code changes were made)

---

## Executive Summary

The x402 implementation is **functional but contains several CRITICAL design issues** that should be addressed before any production traffic. The headline finding: the v1 "EIP-712-style" `PaymentSignature` shape carries a tx hash, not a signature — there is no EIP-712 domain binding, no nonce, and the `validBefore`/`validAfter` window is not cryptographically enforced. The v1 flow effectively trusts the on-chain receipt alone, with the JSON payload acting as advisory metadata that the verifier does NOT cross-check. The BUG-1 payee-bypass fix at `facilitator.ts:920-922` is correctly applied at the **middleware layer** but is **NOT applied inside `verifyEvmPayment` itself** — a defect that any future caller can bypass.

A second cluster of issues centers on **missing replay protection**: the `NONCE_TTL_MS` and `NONCE_REDIS_TTL_SECONDS` constants are exported from `constants.ts` but never imported in `facilitator.ts`. There is no nonce store. The only replay defense is the DB-unique settlement cache keyed on `txHash` — but a malicious actor can re-submit the same tx hash as many times as they like; the second+ submissions get the same receipt, which is fine for idempotency, but a payment with `validBefore = now + 3600` can be replayed after 1 hour and still pass the (advisory) window check.

A third cluster: **the cross-chain endpoints (`/v1/x402/quote`, `/v1/x402/deposit`) are unauthenticated and rate-limit-less**, allowing cache exhaustion, Houdini partner-API quota burn, and deposit-hijack by anyone who learns a `quoteId`. The slippage check at `crosschain.ts:287` uses a hard-coded 0.98, NOT the negotiated `pendingQuote.slippageTolerance`, which both over- and under-protects the user.

**Severity distribution:** 6 CRITICAL · 7 HIGH · 9 MEDIUM · 8 LOW
**Recommendation:** Block the `mockVerifyPayment` path from production (already enforced by `config.ts:225-227` ✓), then address the 6 CRITICAL findings in order. The Surplus x402 signer (CRITICAL #5) is the highest-impact business issue — every Surplus inference call fails 402 until the EIP-712 scheme is fixed.

## CRITICAL Findings

### CRITICAL-1 — No EIP-712 signature verification (the v1 design is tx-receipt-only, not signature-based)

- **Location:** `server/src/x402/facilitator.ts:207-345` (`verifyEvmPayment`); the `signature` parameter is treated as a tx hash throughout
- **Vulnerability:** The route `x402Routes.post("/x402/verify", ...)` (`facilitator.ts:669`) accepts a `PAYMENT-SIGNATURE` header containing a JSON envelope. The `signature` field is then **passed to `verifyEvmPayment` as a tx hash** (line 212: `signature.startsWith("0x") ? signature : "0x" + signature`). The on-chain USDC `transfer` calldata is decoded and matched against `payload.payee` and `payload.payFrom` — but both of those come from the **caller-controlled** JSON payload. There is **no EIP-712 domain**, no `signTypedData` recovery, no chainId binding in the signature verification, and the `validBefore`/`validAfter` fields in the payload are checked at line 397-402 but their cryptographic anchor is the on-chain tx (which has its own block timestamp, not the payload's window).
- **Severity:** CRITICAL — the spec-shaped `PaymentSignature` is a fiction; the security model is "is this an on-chain USDC transfer with matching `to` and `from`". The `validBefore`/`validAfter` window is advisory only.
- **Exploit scenario:** An attacker (or any honest user with a large tx) submits a single $100 USDC transfer to the treasury on-chain. For the next 365 days (the `RECEIPT_EXPIRY_SECONDS` constant at `constants.ts:27`), they (or anyone who observed the tx) can submit the same tx hash as the `signature` of an x402 v1 payment for **any amount up to $100** by lying about `maxAmountRequired` (line 263, 285 only enforce `actualAmount >= requiredAmount`, not the reverse). If the `paymentMiddleware` route is used (line 856-963) the server-side `price` is checked, but the **direct `/v1/x402/proxy/chat/completions` route is now 501 and only does payee-pin, no amount pin** — meaning once that route ships, an attacker can present the same $100 tx against many chat-completion requests.
- **Fix:** Either (a) move to the canonical v2 EIP-3009 `transferWithAuthorization` (sign the authorization tuple, verify with `viem`'s `verifyTypedData` against `USDC_BASE` at `name = "USD Coin"`, `version = "2"`, `chainId = 8453`, `verifyingContract = 0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913`), or (b) at minimum, pin the verifier's `payee` and `maxAmountRequired` to the **server's** expected values inside `verifyEvmPayment` itself (not just in the route handler). The current "client controls both sides of the match" pattern is the same class of bug as BUG-1, just in a different file.

### CRITICAL-2 — No nonce / replay protection (NONCE constants are defined but never used)

- **Location:** `server/src/constants.ts:24-25` (`NONCE_TTL_MS = 600_000`, `NONCE_REDIS_TTL_SECONDS = 600`) is **defined but never imported** in `server/src/x402/facilitator.ts`. Grep confirms 0 usages outside the test stub at `facilitator.test.ts:155`. `verifyPayment` (`facilitator.ts:380-419`) has no nonce store, no `nonce` field in `PaymentPayload` (only the test file's v2 stub has one), and no `usedSignatures` set.
- **Vulnerability:** The only idempotency is the settlement cache keyed on `txHash` (line 451), which only runs AFTER a successful `verifyPayment`. An attacker can submit the same valid `PaymentSignature` to the `paymentMiddleware` route (line 856-963) at line 951-958: `settlePaymentAsync` is called per request, with the same `txHash` → cache hit → returns the same receipt. **This is idempotent for settlement, but the inference side-effect at `c.set("payment", ...)` and `await next()` (line 962) runs EVERY time**, because the middleware never checks "have I already processed this payment?". The `payment` set on `c` is a request-scoped side-channel.
- **Severity:** CRITICAL — the design depends on the upstream inference being idempotent on tx-hash, but `handleChatCompletion` in `crosschain.ts:444` (and the equivalent in `server/src/inference/router.ts:handleChatCompletion`) is **not** idempotent. Each request consumes credits, hits a provider, and produces output. The same tx can drive N chat completions.
- **Exploit scenario:** Attacker deposits $1 USDC to the treasury. Submits 1000 chat-completion requests to `/v1/x402/proxy/chat/completions` (currently 501, but the day it ships) or to a `paymentMiddleware`-protected endpoint with the same `PAYMENT-SIGNATURE` header. Each call passes `verifyPayment` (cached or not, doesn't matter — same result), each call increments `settlementInProgress` counters, each call hits the inference provider. Total: 1000 chat completions for the price of 1.
- **Fix:** Add a nonce field to the v2 `PaymentSignature` (the test already has the shape at `facilitator.test.ts:148-156`); in `verifyPayment`, after a successful EIP-712 verify, attempt `redis.set(\`x402:nonce:${nonce}\`, '1', { NX: true, EX: 600 })` and reject if it returns nil. Reuse the existing `NONCE_REDIS_TTL_SECONDS` constant. Belt-and-suspenders: also store the tx hash in the nonce key so the same tx cannot be re-presented with a new nonce.

### CRITICAL-3 — `verifyEvmPayment` does NOT pin payee to the server's treasury address

- **Location:** `server/src/x402/facilitator.ts:269` and `:291` — `recipient.toLowerCase() !== payeeLower` where `payeeLower = payload.payee.toLowerCase()`. The `payload.payee` is caller-controlled (line 244).
- **Vulnerability:** The BUG-1 payee-bypass fix was applied at the **route handler** layer (lines 793-808 for `/v1/x402/proxy/chat/completions`, lines 920-922 for `paymentMiddleware`). The underlying `verifyEvmPayment` function still only compares the on-chain recipient to the caller-supplied `payload.payee`. This means any **future caller** of `verifyPayment` (e.g., a websocket route, a background job, a new HTTP route, an admin tool) gets the un-pinned version. The fix lives in the wrong layer.
- **Severity:** CRITICAL — the security of the entire x402 v1 flow depends on **every caller** of `verifyPayment` doing its own payee pin. This is exactly the kind of "fix in one place, forget the other" that breeds security regressions.
- **Exploit scenario:** A new endpoint (or a refactor of the existing one) calls `verifyPayment` directly without the surrounding payee-pin logic. Attacker sends a payload with `payee = ATTACKER`, `payFrom = ATTACKER`, and a USDC self-transfer of the required amount. `verifyEvmPayment` returns `{ valid: true, txHash, amount }`. The endpoint accepts it.
- **Fix:** Inside `verifyEvmPayment`, after computing `payeeLower` (line 244), compare against `config.HOUDINI_ADDRESS_TO || config.TREASURY_BASE_ADDRESS` (the same expression used in `x402Routes.post("/x402/settle")` at line 727). Reject if mismatch with error "Payee does not match configured treasury". The route-level check at line 920-922 can stay as defense-in-depth.

### CRITICAL-4 — Settlement cache write happens BEFORE DB insert; receipt is "issued" on cache-only state

- **Location:** `server/src/x402/facilitator.ts:515` (`atomicCacheSet(cacheKey, record);`) is called BEFORE the `db.insert(settlements)` loop at line 518-549. The receipt is signed at line 504 and is already in the in-memory record.
- **Vulnerability:** A caller that calls `getSettlementReceipt` (line 642) or `getSettlementReceiptAsync` (line 632) between the cache write and the DB insert will get a valid-looking receipt that **does not yet exist in the DB**. If the process crashes between line 515 and the DB commit, the in-memory record is lost (no persistence), and the next process restart will not have the receipt. Worse: if `getSettlementReceipt` is used as a "is this settled?" oracle by an external system (the `x-payment-receipt` header at `crosschain.ts:455` and `:461`), that system will accept a receipt that the server has no durable record of. This is a money-handling correctness bug.
- **Severity:** CRITICAL — the `x-payment-receipt` header is signed money (HMAC-SHA256 over the txHash+amount+network+payee+timestamp). Issuing a receipt that the server has no durable record of violates the "signed money" invariant.
- **Exploit scenario:** A burst of settlements arrives. The cache is populated, the HTTP 200 with the receipt is returned to the client. The client uses that receipt elsewhere. The DB write fails (e.g., Postgres down for 30 seconds). The cache TTL is 24 hours (`CACHE_TTL_MS = 86_400_000` at `constants.ts:22`). After restart, the receipt is gone from memory; the client still has a "valid" receipt the server can no longer validate via `verifySettlementReceipt` (line 647) — actually it CAN, because HMAC is deterministic, BUT the server can no longer answer "is this settled?" via `isSettledAsync` (line 619), which queries the DB. The two oracles diverge.
- **Fix:** Move `atomicCacheSet` to AFTER the successful DB insert (line 528). The first-request latency goes up by one round-trip to Postgres, but that's the right trade for signed money. Alternatively, use a write-ahead log (e.g., Redis `SETNX` with the receipt) before the DB write, and treat the DB as a recovery target.

### CRITICAL-5 — Surplus x402 signer is broken (the "TRACKED ISSUE" at surplus.ts:282-364)

- **Location:** `server/src/inference/surplus.ts:282-364`, specifically the `signPayment` function and the inline TRACKED ISSUE comment at lines 303-311.
- **Vulnerability (correctness, not security):** The `signPayment` function uses a custom EIP-712 `Payment` type (lines 336-343) with `name = "Surplus Intelligence"`, `version = "1"`, and `verifyingContract = config.SURPLUS_VERIFIER_CONTRACT ?? config.SURPLUS_SETTLEMENT_CONTRACT` (lines 312-314). The inline comment is explicit: **"TRACKED ISSUE: github.com/oma-ai/oma-ai/issues/surplus-x402-schemes — Stopgap: this route signs against the Surplus settlement proxy (0x0770…c137) as the EIP-712 verifyingContract. The proper scheme-aware signer — `exact` over EIP-3009 TransferWithAuthorization (USDC_BASE, name "USD Coin", version "2", chainId 8453) and `upto` over Permit2 PermitWitnessTransferFrom (0x0000…BA3, name "Permit2", chainId 8453) — is pending. Until that lands, signatures verify against the proxy and the verifier, not the recipient, which is why the previous 0x8581…c402 attempts were silently rejected."**
- The call site is `surplusChatCompletion` at lines 161-194, which receives a 402, parses the `PAYMENT-REQUIRED` header, calls `signPayment`, retries. Every retry fails 402.
- **Severity:** CRITICAL for business — every Surplus inference call goes through this path (when Surplus's discount beats the other providers), so OMA-AI is currently unable to use Surplus's paid-inference capacity. The money side: Surplus charges per-call; if Surplus later accepts these malformed sigs, OMA-AI's wallet would be paying for services the verifier cannot validate. If Surplus silently fails (which is what the comment says), no money moves but OMA-AI falls back to other providers with worse margins.
- **Exploit scenario:** None directly — this is a denial-of-service against OMA-AI's own Surplus path, not a leak. The security risk is forward-looking: when the proper signer is implemented, the existing comment will become stale and any half-fix (e.g., adding `name = "USD Coin"` without flipping to EIP-3009 `TransferWithAuthorization`) could produce signatures that look valid in OMA's audit logs but are worthless on-chain.
- **Fix:** Track the issue in `docs/OMA-X402-CROSSCHAIN-ARCHITECTURE.md` as a known-broken-stopgap. Implement the EIP-3009 `TransferWithAuthorization` for `exact` and the Permit2 `PermitWitnessTransferFrom` for `upto` per the canonical x402 v2 spec. Until then, **disable the Surplus provider entirely** (set its weight to 0 in `MODEL_WEIGHTS` / `PROVIDER_WEIGHTS`) so the router does not attempt this code path.

### CRITICAL-6 — Floating-point arithmetic on USDC amounts (loss of precision, comparison errors)

- **Location:** `server/src/x402/facilitator.ts:262, 284, 929, 930` — `parseFloat` on USDC amounts (6 decimals); `server/src/x402/crosschain.ts:113, 234, 287, 288, 289` — same pattern.
- **Vulnerability:** `parseFloat` is IEEE-754 double. For USDC at 6 decimals, 1 atomic unit is 10^-6. The exact representable doubles are 2^n × m, so values like `0.30000000000000004` are common artifacts. `formatUnits(rawAmount, 6)` (line 261) returns a string like `"0.3"` for 300000 atomic units — `parseFloat("0.3")` returns `0.3`. But `formatUnits(300001n, 6)` returns `"0.300001"`, which `parseFloat` represents as `0.30000099999999999` (or similar). For amounts near 2^53 (≈ 9 trillion USDC), `parseFloat` overflows to `Infinity`, and all comparisons collapse to `Infinity >= requiredAmount = true`.
- The `verifyEvmPayment` check at line 265 is `if (actualAmount < requiredAmount) return false`. The check at line 929 is `if (requestedAmount !== requiredAmount) return false` (strict equality, good — but `parseFloat("0.30") === parseFloat("0.3")` is `true` in IEEE-754 even though the string forms differ).
- **Severity:** CRITICAL for high-value payments, MEDIUM for typical amounts. The check is `<` not `<=`, so an exact match passes. The bigger issue is the inverse: at large amounts where `parseFloat` rounds, an attacker can craft a `maxAmountRequired` like `"9007199254740993"` (= 2^53 + 1) which `parseFloat` rounds to `9007199254740992` (= 2^53). Then the on-chain `rawAmount` of `9007199254740992000000n` (atomic) format-units to `9007199254740992`, and `actualAmount < requiredAmount` is `false` — so the tx is accepted even though the user "asked for" 1 atomic unit more.
- **Exploit scenario:** At low value, the bug is theoretical. At whale scale (large `payTo`/treasury), the difference between 1 USDC and 0 USDC is large. More concerning: a sophisticated attacker can present a `maxAmountRequired` that is **smaller** than the actual `formatUnits` result by 1 atomic unit, exploiting the rounding, and the difference accumulates over many txs.
- **Fix:** Replace all `parseFloat` on monetary amounts with `BigInt` arithmetic. For `formatUnits` outputs, parse as a fixed-point decimal: `const [whole, frac = ""] = s.split("."); const padded = (frac + "0".repeat(USDC_DECIMALS)).slice(0, USDC_DECIMALS); const atomic = BigInt(whole) * 10n ** BigInt(USDC_DECIMALS) + BigInt(padded)`. Compare atomics.

## HIGH Findings

### HIGH-1 — `/v1/x402/quote` is unauthenticated and rate-limit-less

- **Location:** `server/src/x402/crosschain.ts:80` — `crosschainRoutes.post("/v1/x402/quote", async (c) => { ... })` with no `bearerAuth`, no `sessionAuth`, no `rateLimit`.
- **Vulnerability:** Every call hits `houdiniClient.getQuotes(...)` (line 100) and `redis.scan` (line 146) to count cache size. The Houdini partner API has a shared quota across all OMA users; an attacker (or a misbehaving script) can drain the quota in minutes. The Redis scan with `MATCH ${QUOTE_CACHE_PREFIX}*` is O(N) over all keys; with 10K cached quotes, each scan is ~10ms; at 100 req/s the event loop stalls.
- **Severity:** HIGH — quota exhaustion is cross-tenant, cache exhaustion is single-tenant but trivial.
- **Exploit scenario:** `for (let i = 0; i < 1e6; i++) fetch('/v1/x402/quote', { method: 'POST', body: JSON.stringify({...}) })` from a single IP. Houdini quota is gone; legitimate quotes return 502.
- **Fix:** Add `rateLimit({ windowMs: 60_000, maxRequests: 30 })` and a `bearerAuth` (or sessionAuth if you want logged-in users only). Cache hit-before-fetch: if `(fromToken, fromChain, amount, model)` is identical to a recent quote, return the cached `quoteId` instead of re-quoting.

### HIGH-2 — `/v1/x402/deposit` is unauthenticated; `quoteId` is the only authorization

- **Location:** `server/src/x402/crosschain.ts:176` — `crosschainRoutes.post("/v1/x402/deposit", ...)` with no auth. `quoteId` is a 128-bit UUID (line 116), but the `refundAddress` is user-supplied and **not validated** (line 222: passed directly to `houdiniClient.createExchange`).
- **Vulnerability:** The `quoteId` is the only thing preventing attacker deposit-hijack. UUIDs are unguessable in practice, but they leak: they appear in `Pay-Req` response headers (`facilitator.ts:765`), in `payment-URL` query strings (`facilitator.ts:880`, line 747), in browser history, in HTTP referer headers when the user is redirected, in server logs. An attacker who scrapes any of these surfaces can call `/v1/x402/deposit` and claim the deposit for a `refundAddress` of their choice.
- Additionally, the `refundAddress` validation is zero. A user could pass `refundAddress = "0xDEAD..."` of the treasury address itself, or an invalid checksum, or a Solana address (Houdini routes cross-chain; the field needs cross-chain format validation).
- **Severity:** HIGH — funds-loss potential (deposit hijack) and silent loss (bad refund address).
- **Exploit scenario:** The user requests a quote for a $50 ETH → USDC swap. The 402 response includes a `payment-URL` containing the `quoteId` in the query string. The user is redirected to their wallet. The wallet's UI or a referer-leaking redirect exposes the `quoteId` to a third-party analytics endpoint. Attacker scrapes the analytics, claims the deposit, sets `refundAddress = ATTACKER`. The user pays ETH to the Houdini deposit address, the swap completes, but the USDC is sent to the original `houdiniToAddress` (which is fine) — the issue is the **refund path** if the swap fails. If Houdini refunds, the refund goes to the attacker's address.
- **Fix:** Bind the `quoteId` to the originating `userId`/`apiKeyId` at quote creation. At deposit time, require the same auth context. Validate `refundAddress` against chain-specific format (`/^0x[a-fA-F0-9]{40}$/` for EVM, base58 for Solana, etc.). Consider a short deposit-confirmation window (e.g., 5 min) where only the original quoter can claim.

### HIGH-3 — Cross-chain slippage is hard-coded 0.98, not the negotiated value

- **Location:** `server/src/x402/crosschain.ts:287` — `const pendingQuoteMinAmount = (parseFloat(order.toAmount) * 0.98).toFixed(8);`. Compare with line 234: `minAcceptedAmount: (parseFloat(pendingQuote.expectedToAmount) * (1 - pendingQuote.slippageTolerance)).toFixed(8)` — which uses the **negotiated** slippage for the response to the user.
- **Vulnerability:** The user is told one slippage tolerance (the `pendingQuote.slippageTolerance`, default `0.02` from `config.ts:153`). The server's acceptance check uses a hard-coded 0.98 = 2% tolerance. **If the negotiated tolerance is 0.5%** (which the user is told protects them from MEV), the server's hard-coded 0.98 means a 1.5% sandwich-attack loss is **accepted by the server** — but the user was promised 0.5% protection. Conversely, if the negotiated tolerance is 5% (loose), the server's 0.98 is more restrictive than the deal — but that's a UX issue, not a security one.
- **Severity:** HIGH — silent fund loss via sandwich attacks when slippage is tight.
- **Exploit scenario:** A user requests a tight-slippage cross-chain deposit. The MEV searcher observes the Houdini output tx, sandwiches it, drops the output by ~1.5% (well within the hard-coded 0.98 tolerance, but the user expected 0.5% protection). The server accepts the degraded output. The user gets fewer USDC than promised. The MEV bot extracts the delta.
- **Fix:** Replace `0.98` with `(1 - pendingQuote.slippageTolerance)` at line 287. The `pendingQuote` is already in scope (line 192 parses it from Redis).

### HIGH-4 — `/x402/verify` endpoint is unauthenticated; tx-hash oracle for the entire mempool

- **Location:** `server/src/x402/facilitator.ts:669` — `x402Routes.post("/x402/verify", rateLimit({ windowMs: 60_000, maxRequests: 10 }), ...)` with rate limit but no auth.
- **Vulnerability:** Anyone can call `/x402/verify` with any tx hash at 10 req/min. The endpoint queries the live Base RPC, fetches the receipt, and decodes the USDC `transfer` calldata. This is a free oracle for "is this USDC tx hash valid and what was the amount?", which is information that should arguably be behind auth or rate-limited more aggressively.
- More importantly, in **mock mode** (`config.FACILITATOR_MODE === "mock"`), the rate-limited verify endpoint is still hot, but it returns valid for any signature. This is a debug backdoor. If a misconfiguration pushes mock mode to staging, the verify endpoint can be used to confirm forged payments.
- **Severity:** HIGH — combined with CRITICAL-3 (payee not pinned in `verifyEvmPayment`), the unauthenticated verify endpoint can be used to validate forged payments that other unauthenticated endpoints will accept.
- **Exploit scenario:** Attacker calls `/x402/verify` 10 times/min with crafted payloads referencing known USDC self-transfers. Returns valid. Attacker now has 10 forged payment receipts to attempt at any downstream endpoint that calls `verifyPayment` without payee-pinning.
- **Fix:** Either (a) require auth on `/x402/verify` (sessionAuth or apiKey), or (b) lower the rate limit to 2 req/min, or (c) combine with an IP-based allowlist. The endpoint is a diagnostic, not a payment gateway — it should not be a public oracle.

### HIGH-5 — Floating-point + string-amount mismatch in the `paymentMiddleware` strict-equality check

- **Location:** `server/src/x402/facilitator.ts:929-930` — `const requestedAmount = parseFloat(paymentSig.payload?.amount ?? "0"); const requiredAmount = parseFloat(price); if (requestedAmount !== requiredAmount) return ...;`
- **Vulnerability:** The comment at lines 932-934 explains the strict-equality check is intentional. But `parseFloat` introduces precision loss: `parseFloat("100.10") === parseFloat("100.1")` is `true` in IEEE-754 (good, intentional), but `parseFloat("0.1") === parseFloat("0.10000000000000001")` is **also** `true`, and `parseFloat("0.30") === parseFloat("0.3")` is `true`. The check is functionally correct for the "are these the same amount" question, but it has a subtle bug: a payment of `amount = "0.10"` is accepted against a `price = "0.1"` requirement, but a payment of `amount = "0.1000000001"` is **also** accepted. The latter is a 9-atomic-unit overpayment (~$0.000009 at USDC rates). Repeated 1M times, that's $9. Not a real attack, but the `parseFloat` round-trip obscures the actual atomic-unit difference, which makes it hard to reason about ceiling/ceiling-equiv.
- **Severity:** HIGH for principle, LOW for impact. Listed as HIGH because the precision loss hides upstream bugs in amount handling.
- **Fix:** Compare atomically, not via `parseFloat`. See CRITICAL-6 for the BigInt conversion.

### HIGH-6 — Cross-chain error messages leak Houdini internals

- **Location:** `server/src/x402/crosschain.ts:241` — `return c.json({ error: { message: \`Deposit creation failed: ${message}\`, type: "deposit_error" } }, 502);` and `:343` for status.
- **Vulnerability:** `message` is the raw `Error.message` from `houdiniClient.createExchange` / `getOrder`. The Houdini client (lines 208-227 in `houdini-client.ts`) returns the full response body on non-2xx, which can include the partner ID, internal API URLs, rate-limit headers, and chain-specific error codes. An attacker can map the Houdini API surface by triggering different failure modes and reading the error.
- **Severity:** HIGH — the Houdini partner API is a shared resource; surfacing its error details to anonymous callers is a partner-terms violation in most integrations.
- **Exploit scenario:** Attacker calls `/v1/x402/deposit` with `quoteId = ""` (empty, but the schema requires `.min(1)` so a one-character value). The Houdini 400 error includes `{"error": "Invalid quoteId format: Houdini-Internal v2.1 expects UUID v4"}` — the attacker now knows the internal API version and validation rules.
- **Fix:** Map Houdini errors to a stable set of user-facing categories (`quote_expired`, `chain_unsupported`, `rate_limited`, `internal_error`). Log the raw error server-side. Return only the category to the client.

### HIGH-7 — `mockVerifyPayment` logs the truncated signature even though it is meaningless in mock mode

- **Location:** `server/src/x402/facilitator.ts:359-361` — `console.warn(\`[FACILITATOR] [WARN] Mock-mode verification accepted -- signature=${signature.slice(0, 16)}... scheme=${payload.scheme} amount=${payload.amount}\`);`
- **Vulnerability:** This is a minor info-leak: in dev, the log captures the first 16 chars of the signature. In mock mode the signature is whatever the client sent, which could be a real EIP-712 sig from a production system being tested locally. The log line is then visible in CI logs, shared Slack channels, etc. Not a critical leak (16 chars of a sig is not enough to forge), but a hygiene issue.
- **Severity:** HIGH (process) — defense-in-depth on log hygiene, low impact in practice.
- **Fix:** Redact signatures entirely in mock-mode logs: `signature=<redacted>`. Keep the scheme and amount (operational signal), drop the signature material.

## MEDIUM Findings

### MEDIUM-1 — Cache key for verify is `${scheme}:${signature}` (tx hash), pre-warmable and cache-poisonable

- **Location:** `server/src/x402/facilitator.ts:384` — `const cacheKey = ${payload.scheme}:${signature};`
- **Vulnerability:** The verify cache (line 386-394) returns the cached result without re-checking. An attacker can pre-warm the cache for an honest user's tx (e.g., by submitting a verify request with the honest user's signature before the honest user submits), and the honest user will get a stale cache hit. In practice, the cached result is `valid: true` if the tx exists, so the "stale" result is correct, but the **denial-of-service** vector is real: an attacker observing a tx hash can race the legitimate user to pre-warm the cache, then submit a second verify to **overwrite** the cache with `valid: false` if they have a way to do so. Currently the cache is only written on successful verify (the cache is checked at line 386, then verified, then... no, the verify path does NOT write to the cache). So the cache is read-only here, only written via `settlePayment` (line 515, 614). The risk is low.
- **Severity:** MEDIUM — currently benign but the design is fragile.
- **Fix:** Add a write-through on successful verify: `settlementCache.set(cacheKey, { txHash, amount, networkId, payee: payload.payee, settledAt: Date.now(), receipt: '' })`. Cap the cache write by checking the receipt is non-empty. Alternatively, scope the verify cache to `${scheme}:${txHash}:${payee}` so a verify for `payee = A` doesn't serve a verify for `payee = B`.

### MEDIUM-2 — Global boolean `cacheLock` causes head-of-line blocking across all settlements

- **Location:** `server/src/x402/facilitator.ts:114, 136-149, 552-563` — `let cacheLock = false;` is a single shared mutex for the in-memory settlement cache. `atomicCacheSet` (line 136) busy-loops on contention via `setTimeout(() => ..., 0)` (line 138). The settle path also busy-waits on the same lock at line 553.
- **Vulnerability:** Under cache contention, every cache write or read that needs the lock spins. A burst of `settlePaymentAsync` calls (one per request) serializes on this single mutex. With 100 concurrent settlements, the 100th waits for 99 setTimeout ticks plus 99 cache evictions.
- **Severity:** MEDIUM — performance, not security. But it amplifies any DoS that triggers many concurrent settlements.
- **Fix:** Replace the boolean with a `Map<cacheKey, Promise<void>>` lock. The lock is acquired per-key, not globally. The current eviction logic at `evictLRU` (line 127) can be a no-op once the cache is moved to Redis.

### MEDIUM-3 — `cacheLock` setTimeout polling is unbounded; event-loop pressure under load

- **Location:** `server/src/x402/facilitator.ts:138` — `if (cacheLock) { setTimeout(() => atomicCacheSet(cacheKey, record), 0); return; }`
- **Vulnerability:** Recursive `setTimeout(0)` chains. Each call enqueues a timer; the queue grows linearly with contention. Under sustained contention (e.g., 10K req/s on `/v1/x402/proxy/chat/completions`), the timer queue can have 10K pending tasks. Each task does one cache insert; the event loop is dominated by timer firing.
- **Severity:** MEDIUM — performance under load. Easy DoS: just send 10K req/s to a payment-protected endpoint.
- **Fix:** Same as MEDIUM-2 — per-key locking + Redis-backed cache.

### MEDIUM-4 — `evictSettlementInProgressOldest` is called after `set`, so the map can momentarily exceed the cap

- **Location:** `server/src/x402/facilitator.ts:576-580` — `settlementInProgress.set(settleKey, settlementPromise); if (idempotencyKey) { settlementInProgress.set(idempotencyKey, settlementPromise); } evictSettlementInProgressOldest();`
- **Vulnerability:** The set happens before the eviction. If 1001 concurrent settlements arrive, the map reaches 1002 momentarily. The eviction at 580 brings it down to 1000, but the cap is breached. The settlement that's evicted is the OLDEST, which is the most likely to have completed; its `await settlementPromise` will resolve against a missing entry, which is fine. The real risk: if the eviction drops an in-progress settlement that another caller is `await`ing, that caller hangs. But `settlePaymentAsync` is only called from `paymentMiddleware` and not exposed for external awaiting, so the hang is internal.
- **Severity:** MEDIUM — minor invariant breach, no exploit.
- **Fix:** Call `evictSettlementInProgressOldest` before `set`, and re-check the cap with a `while` loop until size is within bounds. Or use an LRUMap (not in stdlib; can be 5 lines of code).

### MEDIUM-5 — `isSettled()` (sync) returns false after restart, even when the tx is in the DB

- **Location:** `server/src/x402/facilitator.ts:628-630` — `export function isSettled(txHash: string, networkId: string): boolean { return settlementCache.has(`${networkId}:${txHash}`); }` checks only the in-memory cache.
- **Vulnerability:** After a server restart, the cache is empty. Any tx that's in the DB will return `false` from this sync function. If a caller (e.g., a websocket route or a `paymentMiddleware` flow) uses the sync version to short-circuit, they will double-process. The `isSettledAsync` version (line 619) is correct (it checks the DB).
- **Severity:** MEDIUM — correctness bug, not a security bug. The `paymentMiddleware` at line 951 calls `settlePaymentAsync` which is the async version, so this is only an issue for direct callers.
- **Fix:** Either remove the sync version or have it return a tri-state (`'unknown' | boolean` — with `'unknown'` if cache miss and DB is unavailable). Document that `isSettled` is a hot-path shortcut, not a source of truth.

### MEDIUM-6 — `validBefore`/`validAfter` checks use server wall clock; no grace period for client clock skew

- **Location:** `server/src/x402/facilitator.ts:396-402` — `const now = Math.floor(Date.now() / 1000); if (payload.validBefore && now > payload.validBefore) return expired; if (payload.validAfter && now < payload.validAfter) return not_yet_valid;`
- **Vulnerability:** A client with a clock 5 minutes ahead presents a payment with `validBefore = now_server + 60`. Server rejects with "expired" because `now_server > validBefore`. The client retries, then the server's clock catches up, the payment is accepted. Not an exploit, but a UX issue. More concerning: a client with a clock 5 minutes BEHIND presents `validAfter = now_server - 300`. Server returns "not yet valid" (because `now_server < validAfter`? No, `now_server > validAfter` is fine; the check is `now < validAfter`, so a past validAfter is always OK). So only `validBefore` is client-clock-sensitive.
- **Severity:** MEDIUM — UX, no security impact.
- **Fix:** Add a 30s grace on both sides: `if (payload.validBefore && now > payload.validBefore + 30) ...` and `if (payload.validAfter && now + 30 < payload.validAfter) ...`.

### MEDIUM-7 — Cross-chain deposit accepts an attacker-controlled `refundAddress` with no validation

- **Location:** `server/src/x402/crosschain.ts:222` — `refundAddress` is passed to `houdiniClient.createExchange(pendingQuote.houdiniQuoteId, houdiniToAddress, refundAddress, pendingQuote.slippageTolerance)`. Houdini routes cross-chain (ETH, Solana, etc.) so the address format is chain-dependent.
- **Vulnerability:** If the from-chain is Ethereum, the refund address should be EVM (0x...40). If Solana, base58. The current code does not validate. A user could accidentally (or attacker could deliberately) pass a Solana address for an Ethereum-from swap, and the refund would be lost on the wrong chain.
- **Severity:** MEDIUM — user-error-driven fund loss, not a direct exploit, but preventable.
- **Exploit scenario:** User pays 0.1 ETH on Ethereum L1, expects refund to their Ethereum L1 wallet, but pastes a Solana address. Houdini fails to refund (or refunds to a dead address).
- **Fix:** Validate `refundAddress` against the from-chain format. Add a Zod refinement on the `depositSchema` (line 38) that switches on `pendingQuote.fromChain`.

### MEDIUM-8 — `evictLRU` only fires when size >= MAX, but `cacheAccessOrder` is never updated on cache HITS

- **Location:** `server/src/x402/facilitator.ts:127-134, 145` — `evictLRU` shifts the FIRST element of `cacheAccessOrder`. `atomicCacheSet` PUSHES to the end of `cacheAccessOrder` (line 145). But the existing entry in the cache (line 386-394) is read on hit, and the hit does NOT move the key to the end of `cacheAccessOrder`. So the LRU is actually FIFO.
- **Vulnerability:** Not a security bug, but the cache does not behave as the name suggests. Hot keys (settled in the last 5 min, queried often) get evicted at the same rate as cold keys. For a 1000-entry cache with 100K unique txs/day, the cache hit rate is near zero for any tx >10 min old.
- **Severity:** MEDIUM — performance and resource waste.
- **Fix:** On cache hit at line 386, move the key to the end of `cacheAccessOrder`: `const idx = cacheAccessOrder.indexOf(cacheKey); if (idx !== -1) cacheAccessOrder.splice(idx, 1); cacheAccessOrder.push(cacheKey);`. Or move the whole cache to Redis with a real LRU policy (`maxmemory-policy allkeys-lru`).

### MEDIUM-9 — `tryParseErrorResponse` in surplus.ts returns `response.statusText` (potentially verbose) on non-JSON errors

- **Location:** `server/src/inference/surplus.ts:461-467` — `return data?.error?.message || response.statusText;`
- **Vulnerability:** `response.statusText` is the HTTP status text, which is generally benign. But for the Surplus endpoint, a 5xx response might include upstream headers or trailers that surface in `statusText` (rare but possible with some proxies).
- **Severity:** MEDIUM — minor info leak.
- **Fix:** Return a sanitized message: `return "Surplus upstream error";`

## LOW Findings

### LOW-1 — `RECEIPT_EXPIRY_SECONDS` is 1 year (31536000) — long-lived receipts make replay detection harder

- **Location:** `server/src/constants.ts:27` — `RECEIPT_EXPIRY_SECONDS = 31536000` (365 days).
- **Risk:** A signed receipt is valid for 1 year. If the receipt is captured in a log or a screenshot, it remains valid for 365 days. Combined with the lack of nonce protection, this is a long replay window.
- **Fix:** Reduce to 7 days (604800) or 24 hours (86400) for high-value payments. Make the expiry configurable per-call.

### LOW-2 — `cacheLock` is awaited via busy-wait in `settlePaymentAsync`

- **Location:** `server/src/x402/facilitator.ts:553-555` — `while (cacheLock) { await new Promise((resolve) => setTimeout(resolve, 1)); }`
- **Risk:** Under sustained contention, the busy-wait pegs a CPU core. Not a vulnerability, but a DoS amplifier.
- **Fix:** Use a proper async lock (e.g., `async-mutex` or a per-key map of resolvers).

### LOW-3 — Mock mode accepts any signature; if `config.ts:225-227` is bypassed, all security is gone

- **Location:** `server/src/x402/facilitator.ts:404-412` — `if (mode === "mock") { if (config.NODE_ENV === "production") throw ...; return mockVerifyPayment(signature, payload); }`
- **Risk:** The defense-in-depth is `config.ts:225-227` (`if (config.FACILITATOR_MODE === "mock" && isProductionEnv) throw ...`). If a future config refactor accidentally moves this check, or if a test environment is run with `NODE_ENV=development` against a real database, mock mode silently accepts forged payments. The check is correct today but the comment at lines 350-353 of `facilitator.ts` says it relies on the config throw — single point of failure.
- **Fix:** Add a runtime check inside `mockVerifyPayment` itself: `if (process.env.NODE_ENV === "production") throw ...`. Defense in depth.

### LOW-4 — `USDC_BASE` is hardcoded to mainnet; no multi-chain support

- **Location:** `server/src/x402/facilitator.ts:239` — `if (tx.to?.toLowerCase() !== USDC_BASE.toLowerCase()) ...`
- **Risk:** If a future caller passes a tx on Base Sepolia, the verification rejects because `USDC_BASE = 0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913` (mainnet) and Sepolia USDC is `0x036CbD53843c392cee76e5b2be5b7c0e9c4f71b54` (different address). The v2 spec comment at line 844 mentions both, but the code only supports mainnet.
- **Fix:** Pass `chainId` to `verifyEvmPayment`, look up the USDC address for that chain. Add a `USDC_BASE_SEPOLIA` constant.

### LOW-5 — `isProductionEnv` includes "preview" — verify alignment with Vercel/Render

- **Location:** `server/src/config.ts:217-218` — `const validProductionEnvironments = ["production", "staging", "prod", "preview"];`
- **Risk:** Vercel uses `production` for prod and `preview` for PR builds. Render uses `production` and `staging` similarly. A `preview` deployment is a PR build — should it really enforce the production secrets checks? The `JWT_SECRET.length < 40` check (line 242-245) will fail on a PR build that doesn't set the env var, which is correct. But the `TREASURY_BASE_ADDRESS` placeholder check (line 230-235) is appropriate for preview too (PRs should not deploy with placeholder addresses). So the current behavior is correct. Just flagging for review.
- **Fix:** No change needed. Document the decision in `OWNER-ONBOARDING.md`.

### LOW-6 — `USDC_DECIMALS = 6` is hardcoded; if USDC changes decimals (unlikely but precedent exists with other stablecoins), all comparisons break silently

- **Location:** `server/src/constants.ts:2` and `server/src/x402/facilitator.ts:261, 283`.
- **Risk:** Low probability event; high impact. No immediate fix needed.
- **Fix:** Add an `assert(USDC_DECIMALS === 6)` at module load. If a USDC variant with different decimals is ever added, the assertion will fire loudly.

### LOW-7 — `_skipIfExists` is destructured but never used in `settlePaymentAsync`

- **Location:** `server/src/x402/facilitator.ts:450` — `const { idempotencyKey, skipIfExists: _skipIfExists = true } = options;`
- **Risk:** Dead code. Ponytail would say delete it. The `_` prefix marks intent-to-ignore, but a future refactor could mistakenly use the variable.
- **Fix:** Remove the destructure if not used.

### LOW-8 — `addSettlementToDlq` is called with `lastError?.message` which may contain PII

- **Location:** `server/src/x402/facilitator.ts:564` — `await addSettlementToDlq(txHash, amount, networkId, lastError?.message || "Unknown error", 1);`
- **Risk:** Postgres error messages can include the row that failed, which includes the `payee` address. If the DLQ is not access-controlled, that's a minor info leak.
- **Fix:** Sanitize the error message before enqueuing: strip addresses (`/0x[a-fA-F0-9]{40}/` → `<address>`).

## What's Working Well

- **Defense in depth on mock mode**: `config.ts:225-227` throws on `FACILITATOR_MODE=mock` in any production-like env. Combined with `facilitator.ts:407-409` (runtime re-check), the mock path is genuinely production-forbidden.
- **HMAC receipt signing**: `facilitator.ts:163-190` uses `timingSafeEqual` on equal-length buffers. The padding-to-equal-length trick (lines 184-188) avoids the early-return leak that `timingSafeEqual` warns about. Good.
- **Settlement lock with Redis NX**: `acquireSettlementLock` (line 19-25) uses `SET NX EX 30` — the correct Redis pattern for distributed locks. The fallback to in-memory-only is documented.
- **Payee pin in BUG-1 fix**: The recent fix at `facilitator.ts:920-922` correctly pins the payee before verification, with case-insensitive comparison (Ethereum addresses are hex). Tests at `facilitator.test.ts:178-215` cover both v1 and v2 exploit variants.
- **Settlement DB unique constraint**: The `pgErr.code === "23505"` handling at line 533-541 catches the race where two concurrent settlements try to insert the same `(txHash, networkId)` pair. The fallback read is correct.
- **Rate limit on verify**: 10 req/min per IP is a reasonable cap that doesn't block legitimate retries.
- **`/v1/x402/proxy/*` bearer-auth**: The cross-chain inference path is auth-walled (line 370), unlike `/v1/x402/quote` and `/v1/x402/deposit`.
- **Houdini lock-value pattern**: The lock at `crosschain.ts:194-206` uses a UUID-as-value to prevent accidental release of another worker's lock (lines 202-206, 243-246). Correct.
- **Settlement cache eviction**: `cleanExpiredCache` (line 116) runs every 5 min, unref'd (so doesn't block shutdown). CACHE_TTL_MS is 24 hours.
- **REFUNDED status audit log**: `crosschain.ts:481` logs `refundTxHash` and `refundAddress` — useful for support tickets.
- **Payment Required response shape**: `facilitator.ts:751-776` correctly includes `payment-URL` and `validBefore`/`validAfter` per the v1 spec.
