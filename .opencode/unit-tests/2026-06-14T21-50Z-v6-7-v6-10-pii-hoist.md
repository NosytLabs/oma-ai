## Behavioral Notes

1. **Key matching uses ends-with semantics** (not strict anchored regex) so common compound names are caught: `userEmail`, `email_address`, `clientApiKey`, `merchantWalletPrivateKey`. The spec's `/^email$/` would miss all of these. The spec's regex was a starting point; practical use is "anything that smells like a credential in the key name".

2. **Addresses (0x + exactly 40 hex) are intentionally KEPT.** They're not sensitive on their own and we need them for debugging deposit/payment flows.

3. **Private-key detection is strict**: exactly 64 hex chars (with or without 0x prefix). 63 or 65 chars is not a key — won't false-positive on hex hashes or short IDs.

4. **Mnemonic detection** uses a 12-24 word pattern with 3-8 letter tokens separated by single whitespace. Common BIP-39 word count, not false-positive on prose.

5. **JSON round-trip** drops non-serializable values (functions, symbols, BigInt) and breaks circular references. Top-level `undefined` is preserved (JSON drops it; we restore the caller's intent).

6. **Ponytail: did NOT add new dependencies**, did NOT create a new module file (extended existing `privacy.ts` — it already had `redactHeaders` / `redactString` / `REDACTED`), kept the test to 2 cases.
