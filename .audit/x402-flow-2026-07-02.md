# x402 Payment Flow & Cross-Page Linking Audit
**Date:** 2026-07-02
**Scope:** Server x402 implementation, frontend x402 surface, deposit/pricing/docs linking, EIP-3009 spec compliance
**Mode:** Read-only (no source modifications)

---

## Executive Summary

The x402 surface is **partially implemented and inconsistently marketed**. The V1 facilitator (server/src/x402/facilitator.ts) verifies on-chain **regular USDC `transfer`/`transferFrom` receipts**, not EIP-3009 `transferWithAuthorization`. The V2 endpoints are scaffolded but return `501 x402_v2_settlement_pending`. The frontend's "x402 Pay-Per-Request" UI panel does not call the x402 protocol — it calls Houdini's payment-link service. Documentation, marketing, and the agent-card.json all claim EIP-3009 gasless behavior that the current code does not implement.

There are **5 P0 issues** that prevent a user from completing a real x402 payment, and **9 P1 issues** that mislead users or break documented flows.

## P0 Issues — Block users from paying

### P0-1: V1 "verifyEvmPayment" does NOT implement EIP-3009 transferWithAuthorization

**Evidence:** `server/src/x402/facilitator.ts:336-484` (`verifyEvmPayment`). It accepts a `signature: string` that is actually a **transaction hash** (L347-349: `const txHash = signature.startsWith("0x") ? (signature as Hash) : ...`). It then:
1. Fetches `getTransactionReceipt({ hash: txHash })` (L362)
2. Checks `tx.to === USDC_BASE` (L374)
3. Decodes calldata as `transfer(address,uint256)` or `transferFrom(address,address,uint256)` (L398, L420)

This verifies a **regular USDC transfer transaction** — the sender paid gas to call USDC's `transfer` method. This is **NOT EIP-3009 transferWithAuthorization** (which is gasless: the user signs an off-chain authorization, and a facilitator submits the on-chain tx).

**Documented as broken in code comments:** `facilitator.ts:1115`: *"v2 uses EIP-3009 transferWithAuthorization (NOT on-chain receipt checks)"*. The codebase itself acknowledges the V1 implementation does not use EIP-3009.

**Marketing that conflicts:**
- `docs/page.tsx:1243`: *"Use the @oma-ai/x402 SDK or any EIP-3009 compatible signer"*
- `docs/page.tsx:1326`: *"Gasless on Solana/Base"*
- `app/src/lib/blog-data.ts:57`: *"EIP-3009 gasless transfers on Base or Solana"*
- `app/src/app/about/page.tsx:43`: *"Base · USDC receipt · EIP-3009 transferWithAuthorization"*
- `app/src/app/about/page.tsx:83`: *"EIP-3009 signature check"*
- `app/src/app/status/page.tsx:60`: *"USDC payment verification · EIP-3009 transfers"*
- `docs/STRATEGY.md:213`: *"Add to docs: complete x402 walkthrough + a Python example with x402-fetch library"*
- `app/src/app/_components/home/x402-banner.tsx:55-58`: *"Your agent sends a request, gets a 402, signs a USDC micropayment on Base, and gets the response — all in one round trip. Settled in seconds, no human in the loop."* (Implies gasless one-trip.)

**Impact:** A user who attempts to follow the docs will try to use `transferWithAuthorization` off-chain signing, send a `PAYMENT-SIGNATURE` whose `signature` field is a 65-byte EIP-712 signature, and the server will treat it as a 32-byte tx hash → `getTransactionReceipt` returns null → 422 "Transaction failed or not found".

### P0-2: V2 verify and settle return 501 (EIP-3009 settlement pending)

**Evidence:** `server/src/x402/v2.ts:260-273` (verify), `v2.ts:281-300` (settle). Both return `501 { error.code: "x402_v2_settlement_pending" }`. The V2 wire format is exercised (pay-req-test returns 402 with base64 PAYMENT-REQUIRED), but the actual settlement is unimplemented.

**Tests confirm:** `server/src/x402/__tests__/v2.test.ts:114-117`, `__tests__/x402.test.ts:371-376`.

**Impact:** No path through V2 actually settles. An agent that follows the v2 spec cannot complete a payment.

### P0-3: `/v1/x402/proxy/chat/completions` returns 501

**Evidence:** `server/src/x402/facilitator.ts:1074-1109`. Returns `501 { error.code: "x402_proxy_pending" }`. The proxy is intentionally not yet enabled.

**Tests confirm:** `server/src/x402/__tests__/facilitator.test.ts:307, 343, 357`. These are "REMAINS 501" tests that explicitly assert the proxy is not yet implemented.

**Impact:** Even if V1 verify accepts a USDC transfer, the chat completion endpoint cannot accept it as a payment method. A user paying x402 cannot actually run inference.

### P0-4: `@oma-ai/x402` SDK referenced in docs does not exist as a package

**Evidence:**
- `app/src/app/docs/page.tsx:1252`: `import { x402Fetch } from '@oma-ai/x402';`
- `app/src/app/docs/page.tsx:1308`: *"Use the `@oma-ai/x402` SDK"*
- `app/src/lib/blog-data.ts:70`: `import { x402Fetch } from '@oma-ai/x402';`

There is no `packages/x402/` directory, no `@oma-ai/x402` package.json, no published SDK. The README (`README.md:135-140`) lists `/x402/verify` and `/x402/settle` as endpoints but provides no SDK.

**Impact:** A developer who copies the docs example will get `Module not found: @oma-ai/x402`. The "Try without signup" CTA and the homepage banner promise a working flow that has no SDK.

### P0-5: The "x402 Pay-Per-Request" UI button does not call the x402 protocol

**Evidence:** `app/src/app/deposit/_components/UnifiedDepositInterface.tsx:644-672` renders an "x402 Pay-Per-Request" panel with checkboxes for "Gasless transactions" / "Works on Solana and Base" / "Automatic token conversion". The button labeled "Create Link" calls `handleCreatePaymentLink` (L324-366) which calls `/api/pricing/crypto` (line 330). That Next.js route forwards to `${apiUrl}/v1/deposit/houdini/payment-link` (`app/src/app/api/pricing/crypto/route.ts:223-236`). The Houdini payment-link service is **not** the x402 protocol — it's Houdini Swap's hosted-payment-link feature.

**Impact:** A user who selects a non-USDC coin (e.g. SOL, BTC), clicks "Create Link", and receives a Houdini payment link will pay Houdini, not OMA. The user is not paying the merchant payee via x402; the user's deposit flow does not exercise `verifyEvmPayment` at all.

## P1 Issues — Visible problems

### P1-1: Mock mode accepts ANY well-formed payment (no payee check in mock path)

**Evidence:** `server/src/x402/facilitator.ts:494-520` (`mockVerifyPayment`). It consumes the nonce (replay protection) but never validates that `payload.payee === SERVER_TREASURY` — it accepts whatever the client sends. Test `server/src/__tests__/x402.test.ts:262-289` explicitly asserts *"mock mode accepts any well-formed payment regardless of payFrom/payee"*.

The C2 payee pin in the public verify endpoint (facilitator.ts:887-895) runs **before** `verifyPayment` is called and only on `/x402/verify` — but `mockVerifyPayment` (called from `verifyPayment`) does not re-check the payee once it sees `cacheKey: ${payload.scheme}:${signature}` — the cache is keyed by signature, not payee.

**Impact:** In dev/test, a developer can mint a receipt with `payee=ATTACKER_ADDRESS`. If the server later switches to mock mode in any non-production env (preview/staging are NOT guarded by `isProductionEnv` per `config.ts:244-245`), an attacker can stamp receipts for non-OBA payees. The `isProductionEnv` list excludes `"development"` and `"test"` — meaning **preview deployments are NOT protected** (preview IS in the list — see `config.ts:244` `["production", "staging", "prod", "preview"]` — preview IS protected).

Wait — the list includes `"preview"`. So all live deployments are protected. **Mock-mode risk is dev-only.** Downgrade to P2.

### P1-2: `UnifiedDepositInterface.detectRoute()` ignores selection; always returns USDC-Base route

**Evidence:** `app/src/app/deposit/_components/UnifiedDepositInterface.tsx:106-114`:
```ts
const detectRoute = useCallback((): RouteInfo => {
  if (!selectedCoin) return ROUTES["usdc-base"];
  if (selectedCoin.id === "usdc-base") return ROUTES["usdc-base"];
  if (selectedCoin.id === "usdc-sol") return ROUTES["usdc-sol"];
  // HoudiniSwap is not configured on this server. Disable the route.
  return ROUTES["usdc-base"];
}, [selectedCoin]);
```
Comment L111-113 admits HoudiniSwap is not configured. Non-USDC selections silently fall through to `usdc-base`, which will then fail downstream because the user thinks they're paying with BTC but the flow sends USDC.

**Impact:** Selecting BTC/SOL/ETH/ADA/XMR/etc. and clicking "Continue" silently treats it as USDC-Base deposit. User sees no error until the wagmi `writeContract` call (which assumes USDC token contract). On the route preview card (L541-562), `route.label` shows "Direct USDC" but the user expected a Houdini route.

### P1-3: The "x402 Pay-Per-Request" route constant exists but is unreachable

**Evidence:** `app/src/app/deposit/_constants.ts:195-203` defines `ROUTES["x402-pay"]` with badge "GASLESS". But `detectRoute()` (see P1-2) never returns it. The UI panel that mentions x402 Pay-Per-Request (UnifiedDepositInterface.tsx:644-672) is shown inside the `step === "route"` view, but the only action is the Houdini "Create Link" button.

**Impact:** Dead UI constant. Confusing for future devs and for anyone reading the codebase.

### P1-4: `/deposit?route=x402&return_to=...` query param has no effect

**Evidence:** The server's 402 pay-req responses set `payment-URL: https://oma-ai.com/deposit?route=x402&network=base&asset=USDC&return_to=...` (`facilitator.ts:1025, 1169`). But the deposit page (`app/src/app/deposit/page.tsx:26-46`) does not read `searchParams`; `UnifiedDepositInterface` has no `route` handling.

**Impact:** The "return to original request after payment" UX pattern is broken — a user who follows the 402 → /deposit link gets the default USDC flow with no context about which model/cost to resume.

### P1-5: Hardcoded `oma-ai.com` domain in payment-URL

**Evidence:** `server/src/x402/facilitator.ts:1025`: `const paymentURL = \`https://oma-ai.com/deposit?route=x402&network=base&asset=USDC&return_to=...`. Same at L1169. Uses literal `oma-ai.com` instead of `config.PRIMARY_DOMAIN` or `config.PUBLIC_API_URL`.

**Impact:** Preview/staging deployments send users to production `oma-ai.com` instead of the staging domain. Also, the `PRIMARY_DOMAIN` env var is defined in `config.ts:63` (defaults to `"oma.ai"`) and is used for SIWE domain binding (auth/middleware.ts). The facilitator should use the same source.

### P1-6: Docs/banner/about claim "Compatible with Coinbase x402 SDK · PayAI · thirdweb" with no verification

**Evidence:** `app/src/app/_components/home/x402-banner.tsx:72`. There are no integration tests, no SDK compatibility matrix, no version pinning. `facilitator.ts:204-214` does support a QuickNode-hosted facilitator (`X402_FACILITATOR_PROVIDER=quicknode`), but QuickNode is not mentioned in the claim. "PayAI" and "thirdweb" are external SDKs not referenced anywhere else in the codebase.

**Impact:** Misleading claim. If a Coinbase SDK client attempts to call this endpoint, it will fail because OMA's V1 wire format does not match Coinbase's V1 spec (Coinbase's V1 used `Pay-Req` header, OMA uses `PAYMENT-REQUIRED`).

### P1-7: `/pricing` "x402 Protocol" banner links to `/deposit`, but `/deposit` has zero x402-specific content

**Evidence:** Pricing L259-286 banner shows "x402 Protocol … recommended" with `<Link href="/deposit">Learn more →</Link>`. The `/deposit` page (`app/src/app/deposit/page.tsx`) renders UnifiedDepositHeader + UnifiedDepositInterface; neither contains a section explaining x402 pay-per-request.

**Impact:** A click on "Learn more →" drops the user onto the standard deposit UI. They never see what x402 actually does, how to use it, or why they should care.

### P1-8: The `_constants.ts` "Houdini / x402 facilitator endpoints" comment is misleading

**Evidence:** `app/src/app/deposit/_constants.ts:208-210`: *"the Houdini / x402 facilitator endpoints"*. The file has only Houdini Swap integration; x402 is separate (`server/src/x402/`).

### P1-9: `treasuryAddress` `undefined` → "Treasury not configured" error displayed to user, deposit disabled

**Evidence:** `app/src/app/deposit/_components/UnifiedDepositInterface.tsx:143-150`: if `process.env.NEXT_PUBLIC_TREASURY_BASE_ADDRESS` is unset, the UI displays *"Treasury not configured. Please set NEXT_PUBLIC_TREASURY_BASE_ADDRESS in your environment variables. Deposits are disabled until treasury is configured."* This is dev/ops copy exposed to end users.

## Fix Recommendations

These are file:line edits to remediate the P0/P1 issues. **Read-only audit — do not apply without review.**

### Fix P0-1: Rename V1 "verifyEvmPayment" → "verifyUsdcTransfer" and add the EIP-3009 path

**File:** `server/src/x402/facilitator.ts:336-484`

1. Add `verifyEip3009Payment(signature, authorization, payload)` that:
