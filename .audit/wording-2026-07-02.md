# OMA-AI wording audit — 2026-07-02

> Read-only review of every claim in `app/src/` and `app/public/` against the
> actual server implementation (`server/src/`, `server/models.json`) and the
> `app/src/lib/models-data.ts` source of truth.
>
> **Bottom line:** the marketing copy consistently overstates what the system
> actually does. The biggest gaps are (1) the `MODELS` array in models-data.ts
> shows **13 hand-curated models with made-up providers** while the real
> catalog is **89 chat + 5 video = 94 Venice-only models**; (2) "gasless" and
> "EIP-3009" claims contradict the x402 facilitator code (V1 verifies on-chain
> USDC `transfer`/`transferFrom` receipts, V2 returns 501); (3) the
> non-Venice providers (OpenAI, Anthropic, Claude, Gemini, OpenRouter,
> Together, AntSeed) are advertised as live when their factory wiring was
> removed; (4) Solana references are pervasive despite the project being
> Base-only.

---

## P0 — fabricated / blatantly false claims

These are claims that would mislead a paying customer and need to be removed
or rewritten before launch.

### P0-1 — Pricing page claims "Gasless payments on Solana and Base"

`app/src/app/pricing/page.tsx:98`

```
desc: "Gasless payments on Solana and Base. Each API request deducts fees automatically.",
```

**Why false:** x402 V1 (`server/src/x402/facilitator.ts:336-484`) verifies an
on-chain USDC `transfer` or `transferFrom` tx receipt. The user pays gas for
that tx themselves. V2 (the spec that adds EIP-3009
`transferWithAuthorization` and would let the facilitator pay gas) is not
implemented — `/v1/x402/proxy/chat/completions` returns 501 (`facilitator.ts:1100-1108`).
Also: "Solana" is never wired (no Solana facilitator, no Solana USDC on
Base settlement).

**Fix:** delete "Gasless payments on Solana and Base" entirely. Replace with
something accurate like: *"x402 pay-per-request on Base. Each request deducts
a USDC micropayment; the user's wallet pays gas for the transfer."*

### P0-6 — x402 docs claim EIP-3009 / transferWithAuthorization for V1 — V1 doesn't do that

`app/src/app/docs/page.tsx:1240, 1243, 1261, 1302-1304, 1305`

```
WWW-Authenticate: X-PAYMENT pay-Req: {"x402Version":"1","scheme":"evm",...
                                  "payee":"0x..."}
# Use viem, ethers, or any EIP-3009 signer to construct transferWithAuthorization
// Sign a USDC transferWithAuthorization (EIP-3009) to the payee.
// Sign a USDC transferWithAuthorization (EIP-3009) on Base and retry
```

`server/src/x402/facilitator.ts:1115-1117` says the opposite:

```
v2 uses EIP-3009 transferWithAuthorization (NOT on-chain receipt checks) and
is a future migration target. The v1 routes below are OMA's pre-spec
internal shape and remain the only payment-protocol endpoints today.
```

V1 verifies an on-chain `transfer`/`transferFrom` receipt and decodes
calldata (`facilitator.ts:388-454`). The PAYMENT-SIGNATURE header in V1 is
just `{x402Version, signature, authorization, payload}` where `signature`
holds a tx hash. There is no EIP-3009 signature anywhere on V1.

**Fix:** rewrite the docs code blocks. V1 client flow:

```
1. Send a USDC `transfer` to the payee from your wallet.
2. Receive the tx hash back.
3. Retry the API call with PAYMENT-SIGNATURE: <base64(json containing txHash)>
```

The V2 (EIP-3009) path can stay as a "Coming soon" note pointing at
`https://github.com/coinbase/x402`. As written, the docs are flat-out wrong
and would send an agent integrator down a dead end (signing an
EIP-3009 tuple that OMA will then 402 on).
