# x402 EIP-3009 fix — 2026-07-02

**Branch:** `main` (working tree, not yet committed)
**Scope:** `server/src/x402/facilitator.ts` V1 verify path. Adds EIP-3009 `transferWithAuthorization` as the canonical V1 wire; keeps the legacy on-chain-receipt path as a back-compat fallback.
**Result:** All 729 tests pass (713 pre-existing + 16 new). Typecheck + lint clean.

---

## Audit context

Per `.audit/x402-flow-2026-07-02.md` (P0-1):

> `server/src/x402/facilitator.ts:336-484` (`verifyEvmPayment`) accepts a `signature: string` that is actually a **transaction hash**… fetches `getTransactionReceipt({ hash: txHash })`… decodes calldata as `transfer(address,uint256)` or `transferFrom(...)`. This verifies a **regular USDC transfer transaction** — the sender paid gas. This is **NOT EIP-3009 transferWithAuthorization** (which is gasless).

> Documented as broken in code comments: `facilitator.ts:1115`: *"v2 uses EIP-3009 transferWithAuthorization (NOT on-chain receipt checks) and is a future migration target."*

Docs and marketing in 7+ files claim EIP-3009 gasless behavior. This commit makes the V1 path actually do that.

## What changed

### 1. `server/src/x402/facilitator.ts` — EIP-3009 V1 verify path

**New helpers (added near top of file, after constants):**

| Symbol | Purpose |
|---|---|
| `USDC_EIP712_DOMAIN` | EIP-712 typed-data domain for USDC on Base: `{ name: "USD Coin", version: "2", chainId: 8453, verifyingContract: USDC_BASE }` |
| `EIP3009_TRANSFER_WITH_AUTH_TYPES` | Typed-data types: `TransferWithAuthorization(from,to,value,validAfter,validBefore,nonce)` |
| `USDC_EIP3009_ABI` | Minimal viem ABI for `transferWithAuthorization`, `authorizationState`, `balanceOf` |
| `Eip3009Authorization` interface | Wire shape: `{ from, to, value, validAfter, validBefore, nonce }` |
| `isEip3009Authorization()` | Type-guard — accepts value-or-string for numeric fields |
| `recoverEip3009Signer()` | Calls `viem.recoverTypedDataAddress` with the canonical domain |
| `syntheticEip3009TxHash()` | Deterministic placeholder when no facilitator key is configured |
| `simulateEip3009Transfer()` | `eth_call` against USDC — catches double-spend / balance issues pre-submit |
| `submitEip3009Transfer()` | Real `writeContract` using `FACILITATOR_PRIVATE_KEY` when configured |

**New verify path (`verifyEip3009Payment`)** runs through 8 steps:
1. **Replay protection** — `consumeNonce()` before any RPC (CRIT-2 preserved)
2. **Parse** the JSON EIP-3009 tuple from `authorization`
3. **Pin payee** to `SERVER_TREASURY` (reject mismatches)
4. **Pin amount** ≥ `payload.maxAmountRequired`
5. **Time bounds** — reject `validBefore <= now` or `validAfter > now`
6. **Recover EIP-712 signer** via `recoverTypedDataAddress`; reject if `recovered != authorization.from`
7. **Simulate** via `eth_call` — catches nonce-already-used / balance issues
8. **Settle**:
   - If `FACILITATOR_PRIVATE_KEY` set → submit real `transferWithAuthorization` tx (gasless for user)
   - Else → return synthetic keccak256-derived txHash so settle cache + receipt still work

**Dispatcher (`verifyEvmPayment`)** auto-routes based on `authorization` shape:
- JSON + complete EIP-3009 tuple → `verifyEip3009Payment`
- JSON + missing fields → clear "missing required EIP-3009 fields" error
- Non-JSON + 65-byte signature → clear "must be JSON-encoded EIP-3009 tuple" error
- Non-JSON + 32-byte signature → legacy `verifyUsdcTransferReceipt` (back-compat)

**Legacy path (`verifyUsdcTransferReceipt`)** is the pre-existing on-chain-receipt check, renamed and moved out of the dispatcher. It still works for any pre-existing client that submits a USDC transfer on its own and sends the tx hash as `signature`.

**Updated comment block** at `facilitator.ts:1505` (was the v2 spec note) now documents the new V1 wire shape and the audit fix.

## How a real client uses this

```typescript
// 1. Client signs EIP-712 TransferWithAuthorization typed data
const domain = {
  name: "USD Coin",
  version: "2",
  chainId: 8453,
  verifyingContract: "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
};
const types = {
  TransferWithAuthorization: [
    { name: "from", type: "address" },
    { name: "to", type: "address" },
    { name: "value", type: "uint256" },
    { name: "validAfter", type: "uint256" },
    { name: "validBefore", type: "uint256" },
    { name: "nonce", type: "bytes32" },
  ],
};
const message = {
  from: userAddress,
  to: TREASURY_ADDRESS,
  value: parseUnits("1.00", 6), // 1 USDC in atomic units
  validAfter: now,
  validBefore: now + 300,
  nonce: randomBytes(32),
};
const signature = await walletClient.signTypedData({ domain, types, primaryType: "TransferWithAuthorization", message });

// 2. POST /x402/verify with PAYMENT-SIGNATURE header
await fetch("/x402/verify", {
  method: "POST",
  headers: {
    "PAYMENT-SIGNATURE": JSON.stringify({
      x402Version: "1",
      signature,                                                  // 65-byte EIP-712 sig
      authorization: JSON.stringify(message),                     // EIP-3009 tuple
      payload: {
        x402Version: "1",
        scheme: "evm",
        networkId: "base",
        asset: "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
        amount: "1.00",
        payee: TREASURY_ADDRESS,
        payFrom: userAddress,
        maxAmountRequired: "1.00",
        validBefore: message.validBefore,
        validAfter: message.validAfter,
        nonce: message.nonce,
      },
    }),
  },
});
// → { valid: true, txHash: "0x...", amount: "1.000000", networkId: "base" }

// 3. (optional) POST /x402/settle with the txHash to get a signed HMAC receipt
```

**User experience:**
- No gas for the user (facilitator pays it via `FACILITATOR_PRIVATE_KEY`)
- Single round-trip: sign + verify + settle is one HTTP call to `/x402/verify` (the verify path internally submits the on-chain tx when `FACILITATOR_PRIVATE_KEY` is configured)

## Remaining work / known limitations

### 1. `FACILITATOR_PRIVATE_KEY` is not yet configured in production

The verify path submits the real on-chain tx only when `FACILITATOR_PRIVATE_KEY` is set. In dev / preview deployments where it's unset, the path returns a **synthetic txHash** (keccak256 of tuple+sig) so the verify+settle cache key still works.

**Operational impact:**
- Dev/preview: clients can verify and get receipts (synthetic) but no on-chain settlement happens.
- Production (when `FACILITATOR_PRIVATE_KEY` is wired up in render.yaml / env): clients get gasless real USDC transfers on Base.

**Action item:** Configure `FACILITATOR_PRIVATE_KEY` for the facilitator wallet in production render.yaml. Wallet must be funded with a small amount of ETH for gas (sub-cent per USDC transfer on Base L2). See `.audit/server-fixes-2026-07-02.md` follow-ups.

### 2. The V2 routes (`/v2/x402/verify`, `/v2/x402/settle`) still return 501

`server/src/x402/v2.ts` was intentionally removed (see `.audit/server-fixes-2026-07-02.md`); the audit recommended removing all references until EIP-3009 + facilitator key were available. With this fix, those references can now be restored, but that's out of scope for this commit. The V1 verify path now serves both clients (the legacy receipt-check shape and the new EIP-3009 shape), so V2 can be re-introduced incrementally.

### 3. No live on-chain integration test

`eip3009.test.ts` mocks viem's RPC calls; it doesn't exercise a real Base mainnet USDC contract. A live test would require a funded test wallet + signing an actual `transferWithAuthorization` against a testnet (Base Sepolia). The existing live-on-chain tests in `verify-usdc-on-chain.isolated.test.ts` follow the same mock pattern. Out of scope.

### 4. Marketing copy still says EIP-3009 in 7+ files

`.audit/x402-flow-2026-07-02.md` P2-1 lists the files:
- `app/src/app/docs/page.tsx:1243, 1326` — "EIP-3009 compatible signer", "Gasless on Solana/Base"
- `app/src/lib/blog-data.ts:57` — "EIP-3009 gasless transfers"
- `app/src/app/about/page.tsx:43, 83` — "EIP-3009 transferWithAuthorization"
- `app/src/app/status/page.tsx:60` — "EIP-3009 transfers"
- `app/src/app/_components/home/x402-banner.tsx:55-58` — "one round trip"
- `app/src/app/swap/page.tsx:109` — "x402 gasless"

**With this fix the implementation matches the copy for the first time.** However, "Gasless on Solana" is still aspirational — this commit only adds Base support (USDC_BASE). Solana support would need a separate `solana-verify.ts` integration.
